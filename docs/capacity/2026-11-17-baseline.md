# Capacity report 2026-11-17: first k6 baseline and Level 1 fixes

- Owner: backend
- Environment: local Docker Desktop (Windows laptop, 8 vCPU visible to containers). **Indicative only**; staging on
  real SSD storage must repeat this before launch (ADR 0020).
- Load: `infra/scripts/load/baseline.js`, constant arrival rate ≈ 57 req/s (business page 20/s, feed 20/s, slots 10/s,
  search 5/s, booking create 2/s), 70 s–2 min per run.
- Targets: reads p95 < 200 ms, booking create p95 < 300 ms, no 5xx.

## Results (one change at a time)

| Step | Change | Reads p95 | Booking p95 | Notes |
|---|---|---|---|---|
| 0 | Baseline | 1.86 s | 2.81 s | only 41 of 57 req/s served, 1032 dropped iterations, statement timeouts on booking |
| 1 | Pure ASGI middleware (request id, metrics, CSRF) instead of 3× BaseHTTPMiddleware; gunicorn access log off (nginx logs) | **195 ms** | 763 ms | 0 errors, full rate served |
| 2 | Booking create stops re-loading business + service | 231 ms | 891 ms | within run-to-run noise; kept (fewer queries) |
| 3 | `RSV_API_WORKERS=4` (from 2) | 294 ms | 938 ms | no gain → reverted to 2 |
| diag | `synchronous_commit=off` (diagnostic only, reverted) | 97 ms | 184 ms | all targets met |

## Root cause
1. **Step 0 → 1:** API CPU saturated at 2 workers (~200%). Profiling showed per-request overhead in Starlette's
   BaseHTTPMiddleware (task group + memory streams per layer, three layers). Fixed.
2. **Remaining gap (booking p95, read tail):** during load Postgres sessions show `IO:WALSync` on `COMMIT`.
   `pg_test_fsync` on the Docker Desktop volume: fdatasync 5.4 ms/op (≈185 ops/s). Every write transaction (booking,
   outbox, idempotency, refresh) waits for this. Async commit removes the gap entirely, which confirms the disk is
   the bottleneck, not the code. A real NVMe/SSD VM does fdatasync in well under 1 ms.

## Options for the remaining gap
| Option | Cost | Expected gain | Decision |
|---|---|---|---|
| Staging/production on SSD-backed VM (planned anyway) | none extra | removes the fsync wait | **Do** — re-run baseline on staging |
| `synchronous_commit=off` globally | risk: lose last ~600 ms of commits on crash | large | **Rejected** (RPO, money and bookings) |
| `synchronous_commit=off` per transaction for non-critical writes (view counts, analytics) | small code change | moderate | Later, only if staging still misses targets |
| Redis caches for business page / slots | invalidation code | reads only | Later, trigger in ADR 0020 |
| More API workers / replicas | CPU, memory | none measured | Not now |
