# Capacity report 2026-11-17: first k6 baseline and Level 1 fixes

- Owner: backend
- Environment: local Docker Desktop (Windows laptop, 8 vCPU visible to containers). **Indicative only**; staging on
  real SSD storage must repeat this before launch (ADR 0020).
- Load: `infra/scripts/load/baseline.js`, constant arrival rate ≈ 57 req/s (business page 20/s, feed 20/s, slots 10/s,
  search 5/s, booking create 2/s), 70 s–2 min per run.
- Targets: reads p95 < 200 ms, booking create p95 < 300 ms, no 5xx.

## Results (one change at a time)

| Step | Change | Reads p95 | Booking p95 | Notes |
|---|---|---|---|---|
| 0 | Baseline | 1.86 s | 2.81 s | only 41 of 57 req/s served, 1032 dropped iterations, statement timeouts on booking |
| 1 | Pure ASGI middleware (request id, metrics, CSRF) instead of 3× BaseHTTPMiddleware; gunicorn access log off (nginx logs) | **195 ms** | 763 ms | 0 errors, full rate served |
| 2 | Booking create stops re-loading business + service | 231 ms | 891 ms | within run-to-run noise; kept (fewer queries) |
| 3 | `RSV_API_WORKERS=4` (from 2) | 294 ms | 938 ms | no gain → reverted to 2 |
| diag | `synchronous_commit=off` (diagnostic only, reverted) | 97 ms | 184 ms | all targets met |

## Root cause
1. **Step 0 → 1:** API CPU saturated at 2 workers (~200%). Profiling showed per-request overhead in Starlette's
   BaseHTTPMiddleware (task group + memory streams per layer, three layers). Fixed.
2. **Remaining gap (booking p95, read tail):** during load Postgres sessions show `IO:WALSync` on `COMMIT`.
   `pg_test_fsync` on the Docker Desktop volume: fdatasync 5.4 ms/op (≈185 ops/s). Every write transaction (booking,
   outbox, idempotency, refresh) waits for this. Async commit removes the gap entirely, which confirms the disk is
   the bottleneck, not the code. A real NVMe/SSD VM does fdatasync in well under 1 ms.

## Options for the remaining gap
| Option | Cost | Expected gain | Decision |
|---|---|---|---|
| Staging/production on SSD-backed VM (planned anyway) | none extra | removes the fsync wait | **Do** — re-run baseline on staging |
| `synchronous_commit=off` globally | risk: lose last ~600 ms of commits on crash | large | **Rejected** (RPO, money and bookings) |
| `synchronous_commit=off` per transaction for non-critical writes (view counts, analytics) | small code change | moderate | Later, only if staging still misses targets |
| Redis caches for business page / slots | invalidation code | reads only | Later, trigger in ADR 0020 |
| More API workers / replicas | CPU, memory | none measured | Not now |

## Second round: readiness review and Level 2 checks (same day)

### Readiness review (`infra/scripts/capacity_review.sql`, pg_stat_statements now preloaded)
- Buffer cache hit 99.98%, 0 deadlocks, no lock waits, 24 of 100 connections, no missing-index seq scans, outbox empty.
- Most expensive query: hybrid search (4.2 ms mean). Its HNSW index was never used: the `allowed` CTE is
  materialised and scanned on every search, so cost grows with the document count. Fine at 204 documents;
  **revisit when search p95 passes 150 ms or documents pass ~100k** (ADR 0020 trigger).
- 1 dead letter: `posts.published` / `RuntimeError('Event loop is closed')`, from the first baseline run.

### Worker connection reuse (Level 1)
Cause of the dead letter and of 562 new DB connections in one 70 s run: each Celery task ran in a fresh event
loop with a NullPool engine, and the process-wide Redis client stayed bound to the first task's closed loop.
Now one loop and a 2+2 pool per worker process (`app/workers/runtime.py`): **562 → 31 new connections** per run,
outbox fully drained, 0 worker errors. Regression test fails on the old code ("attached to a different loop").
The worker also had no statement timeout; it now shares `build_engine` with the API.

### Replica failover (exit criterion: one replica failing loses no data)
`--scale api=2`, k6 baseline, `docker kill` of one replica mid-run (a crash, not a graceful stop):
| Run | Gateway config | Failed requests | Bookings confirmed vs DB rows | Notes |
|---|---|---|---|---|
| 1 | variable `proxy_pass` | 0 / 4117 | 141 = 141, no duplicates | stalls up to 5.4 s (5 s connect timeout to the dead IP) |
| 2 | + 2 s connect timeout at http level | 0 / 4080 | 140 = 140 | worse: server-level 5 s still applied, dead IP retried for the 10 s DNS TTL |
| 3 | `upstream … resolve max_fails=1` (nginx 1.27.5), 2 s connect timeout | 0 / 4076 | 138 = 138 | **no slow requests after the kill**; 2 in-flight requests reset and retried |
| 4 | two warm replicas, no kill | 0 / 4137 | — | reads p95 294 ms: no gain from a second replica on one laptop |

A slow window in the first 10 s of run 3 (before the kill) could not be separated from laptop noise.
With a single replica a restart still has a short gap (one 504 seen while the container was recreated);
zero-downtime deploys need two replicas and a rolling start (deferred per ADR 0020).

connections pass 70% of max or a second app VM exists; re-measure on staging first.
